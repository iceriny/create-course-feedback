# 课程反馈生成器全面审查

审查日期：2026-09-09；项目版本：0.7.0。

本轮审查代码、实际浏览器界面和操作路径，执行测试、构建与 lint。没有修改业务代码，没有调用真实 AI 生成或发送学生数据。浏览器操作使用本地开发服务与虚构班级、学生。以下区分实际复现、代码确认和待测推断；产品建议属于设计判断。

## 1. 总体判断

项目已经具备小班教师常用的核心能力：复用课程与名单、结构化记录表现、批量生成、单人重做、自定义模板和复制反馈。领域逻辑、生成编排、存储仓库也已有分层，并非需要推倒重写。

目前最影响使用价值的是三件事：学生与反馈的对应关系不够可靠；一次课的工作不能完整恢复；生成后缺少高效的人工校对与交付流程。视觉上有成熟组件库的一致性，但页面仍以纵向表单堆叠为主，主要动作、进度和异常不够集中。

建议产品目标收敛为“让教师可靠地完成一次课的反馈”，先建立完整工作闭环，再增加更多生成能力。

| 维度 | 现状判断 | 优先方向 |
| --- | --- | --- |
| UI 审美 | 基础一致，但阴影重、留白分配失衡、层级弱 | 轻量工作台、统一间距、清晰主操作 |
| 响应式 | 手机端已复现严重裁切 | 去固定最小宽度，窄屏单列 |
| 操作便捷度 | 熟练用户可操作，首次使用与大量录入负担较重 | 明确文案、表格式录入、连续处理 |
| 工作流 | 生成链路具备，草稿恢复和人工确认环节不足 | 课次草稿、审阅、复制状态 |
| 性能 | 构建成功，存在大包和广泛重渲染风险 | 测量流式更新，再缩小订阅范围 |
| 可靠性 | 排序错位已复现，其他高影响风险有明确代码路径 | 稳定身份、过期任务保护、存储恢复 |
| 工程质量 | 测试和分层已有基础，完整用户流程覆盖不足 | 补少量关键集成与端到端测试 |

## 2. 应先修复的确定问题与高影响风险

### P1：排序后学生课堂表现错位【浏览器复现】

复现步骤：建立名单 `Zoe, Amy`，分别在整体表现填写“Zoe 的专属观察”和“Amy 的专属观察”，点击名单排序。排序后 Amy 卡片显示“Zoe 的专属观察”，Zoe 卡片显示“Amy 的专属观察”。

原因是名单和输出状态排序了，Ant Design Form 中按 index 保存的原始输入没有同步移动；卡片 key 也使用 index。之后生成会读取错误学生的表现，这直接影响交付内容的准确性。

相关代码：`src/store/rosterStore.ts:88`、`src/components/StudentsList.tsx`、`src/components/StudentContentCard/StudentInputs/V2Input.tsx`、`src/services/ai/feedbackGeneration.ts`。

建议为学生建立稳定 ID，以 ID 关联表单、输出与任务，排序只改变展示顺序。不要用姓名替代稳定 ID，否则改名和同名学生仍有问题。短期修补至少需要同步重排输入，但无法同时解决在途请求问题。

验收：排序、插入、删除、改名后，输入、输出与任务始终跟随同一学生；覆盖 V1/V2 混合名单。

### P1：在途任务可能回写给错误学生，重复批量生成可能互相覆盖【代码确认路径，未调用真实 AI】

生成任务保存 `index`，流式数据与完成回调均执行 `updateStudentInfo(task.index, ...)`。生成期间仍可排序、切班或调整名单，回写没有校验班级/课次、学生 ID 和当前 taskId。批量生成也没有过滤正在生成的人，队列入口没有去重。单人按钮虽禁用 loading 状态，批量入口仍能重复入队。

相关代码：`src/services/ai/generationOrchestrator.ts:103`、`:245`、`:331`，`src/hooks/useFeedbackGeneration.ts`，`src/components/MainUI.tsx`。

建议以课次 ID、学生 ID、taskId 保护回写；同一人的任务去重；任务管理独立于可变的提示词界面状态。增加取消能力。临时禁用名单变更可降低风险，但仍需处理旧任务晚到的情况。

验收：生成途中切班、排序、重复点击、修改提示词，旧任务均不能污染当前结果。

### P1：修改名单会清空已有结果，刷新后无法恢复完整课次【代码确认】

`updateStudentsFromRawValues` 与 `loadStudentsFromStorage` 均通过 `createStudentsInfo` 初始化空内容。即使只是新增一个学生，也会重建所有人的输出和启用状态。原始课堂表现位于 Form，生成结果位于运行时 store，名单仓库只保存姓名、性别、输入版本。已有 prompt trace 是有限条数的诊断记录，不能等同于可恢复的课次草稿。

相关代码：`src/store/rosterStore.ts:164`、`src/domain/student.ts`、`src/services/persistence/rosterRepository.ts`。

建议以课次保存课程信息、学生关联、原始表现、生成结果、人工修改和处理状态。新增学生时只初始化新人；重新生成保留上一次可用结果，成功后再替换。显示“正在保存 / 已保存 / 保存失败”，支持恢复草稿。

验收：添加一个学生不影响已完成的人；刷新、切班后能恢复原始输入和结果；新一课不会混入上次表现。

### P1：流式解析把网络分块当成完整事件【代码确认】

`API._sendMessage` 每次读取网络 chunk 后直接按换行拆分并解析 JSON，没有保留跨 chunk 的未完成行。一个合法事件被网络拆成两段时，第一段 JSON 解析失败便触发失败回调，后一段可能被跳过。上层会重试，但原请求仍可能继续读流，产生额外等待与请求。

同一路径没有检查 `response.ok`。如果 401/429 等错误返回普通 JSON，可能被读到结束后按完成处理，再归类为内容为空的待确认结果，不能准确体现请求失败。也未见超时和 AbortController 取消路径。

相关代码：`src/AI_API/API.ts:516`、`:539`，`src/services/ai/AIClient.ts`。

建议保留跨 chunk 缓冲，按完整 SSE 事件解析；分开处理 HTTP 错误、解析错误、超时和主动取消。401 等配置错误直接引导修正；临时网络错误和限流再按策略重试。

验收：同一事件在任意字节位置拆分、中文跨字节、多个事件合并到一块、401、429、断网、挂起流均有确定结果。

### P1：批量导出可以包含未完成或失败残留内容【代码确认】

“导出已选且有反馈”只检查非空和启用状态，没有检查 loading、failed 或 needs_review。流式生成已输出几个字时即可满足条件；失败后残留的部分文本也能进入批量导出。按钮提示本身说的是“有反馈”，但工作流容易让用户误认为这些内容已可交付。

相关代码：`src/services/feedback/feedbackTemplate.ts:70`、`src/components/MainUI.tsx:689`。

建议区分生成完成与教师确认，默认复制确认完成的内容；待确认项明确展示数量并允许审阅。基础规则检查通过不应暗示事实已经核实。

验收：生成中、失败、空内容不会混入完成结果；待确认内容可被明确识别和处理。

### P1：手机界面被裁切【390 × 844 实际复现】

课程卡片 `minWidth: 800px`，页面左右各 50px padding，主网格固定 2/16/6 分栏；全局 `overflow-x: hidden` 把溢出内容隐藏。手机下只能看到卡片左部，日期和其他右侧内容超出屏幕，名单挤到下方，页头标题换行溢出。

相关代码：`src/components/CourseInfoCard.tsx:149`、`src/components/MainUI.tsx:455`、`src/Page.tsx`、`src/index.css`。

建议窄屏单列、16px 页面边距，名单改为可收起区域；日期表单与卡片头允许换行。先修布局再讨论移动端视觉细节。

验收：390、768、1280px 宽度下主要操作均可见可用，不靠隐藏溢出掩盖问题。

### P2：首次更新弹窗难退出【浏览器复现】

首次本地打开出现从 0.1.0 至 0.7.0 的完整更新记录；顶部关闭按钮点击无效，底部确认才能退出。Modal 没有绑定 `onCancel`。版本详情还是逐个串行请求。

相关代码：`src/updateInfo.tsx:43`、`src/Version.ts`。

建议首次进入展示简短使用引导；更新只展示本次要点，历史记录放到独立入口；关闭按钮、Esc 和确认行为一致。

### P2：备份“全部信息”与实际范围不符【代码确认】

备份遍历 localStorage，对每个值强行 `JSON.parse`，无法解析的原始字符串被跳过。输入联想存在 Dexie 中，也没有进入备份；当前表单和运行时反馈本身未完整持久化。导入逐项写入后不重新加载 store，没有清晰的完成或失败反馈。文件输入没有添加到 body 却调用 `removeChild`，会产生 DOM 异常；这不等同于文件回调一定失败，但应修正。

相关代码：`src/components/SettingsDrawer.tsx:25`、`:50`、文件导入按钮，`src/store/InputAssistantStore.ts`。

建议定义带版本号的明确备份格式，覆盖真实业务数据；密钥默认不包含，明确可选范围；导入前预览数量和冲突处理方式，导入后重载业务状态。存储配额不足时保留现有内容并明确提示，不应仅依赖控制台。

验收：导出到干净环境导入，课程、名单、模板、短语与课次草稿一致；无效文件和存储失败有明确反馈。

## 3. UI 审美与信息架构

### 推荐视觉方向

采用安静、紧凑、适合长时间文字工作的教师工作台。保留 Ant Design，减少大面积阴影与多层边框，使用浅灰背景、白色工作区、单一主色和清晰文字层级。品牌识别通过页头、颜色与少量细节建立，不需要增加大插画或装饰性动效。

当前课程卡片阴影扩散到 80px，学生卡片也有较重阴影，容易显得发灰；页面左侧空列、72px 横向 gutter 和字段 18/24 宽度叠加，占用了实际录入空间。初始名单只是一个窄输入框，没有标题和说明，无法清楚传达用途。

建议统一 8/16/24px 间距体系，桌面名单区约 220–260px、工作区弹性伸展；主操作保留一个实心按钮。标题表达当前任务，次级信息弱化。版本号和署名不应占据与当前课程同等的注意力。

### 入口与文案

| 当前 | 建议 | 目的 |
| --- | --- | --- |
| AI 优化 | 生成反馈（12人） | 明确动作与范围 |
| 重新或单独生成 | 生成反馈 / 重新生成 | 根据当前状态显示 |
| V1 / V2 | 简要记录 / 分项记录 | 消除版本术语 |
| 两个相同文件图标的悬浮按钮 | 复制反馈 + 范围菜单 | 减少记忆和误点 |
| 省略号设置入口 | 设置图标 + 可见标签 | 提高发现性 |
| 思考 / 内容 | 生成详情 / 反馈正文 | 优先呈现交付内容 |
| 检查通过 | 未发现格式问题 | 避免暗示事实已验证 |
| 著名（模板标签） | 签名 | 修正文案错误 |

状态需要文字和图标共同表达。不要依靠蓝色与灰色区别两种复制范围，也不要把必需操作只放进悬停提示。图标按钮应有可读名称，可点击的删除图标应使用真正的按钮以支持键盘。

### 两种合理布局

小班和集中撰写适合“左侧名单 + 右侧当前学生编辑与预览”，减少滚动并突出当前工作。30 人以上且记录较短时，更适合“一人一行”的紧凑录入视图，列出表现与生成状态，选中后展开完整反馈。

两者无需同时开发。先观察真实班级规模、每人记录长度和设备，优先实现高频场景。不要把完整操作拆成不可返回的强制向导；教师常会边看结果边补录信息。

## 4. 操作便捷度与工作流优化

建议的一次课流程：

```mermaid
flowchart LR
    A[选择班级与本次课程] --> B[录入每人表现]
    B --> C[生成未完成反馈]
    C --> D[校对与修改]
    D --> E[确认并复制]
    E --> F[保存本次记录]
    D --> B
```

课次草稿应贯穿上述所有阶段自动保存，最后的保存表示课次归档。

1. **开始一次课**：选择班级后展示上次课程摘要，提供“复用课程内容”；选择历史课程默认保留本次日期，另设明确的“恢复历史课次”。目前加载历史会同时设置时间，选择班级也会推算上周日期，用户较难判断哪些字段被改变。
2. **录入观察**：名单粘贴支持换行、中文逗号、顿号、制表符；导入前可预览。当前解析主要支持英文逗号并按姓名去重，同名学生无法独立表达。
3. **减少重复填写**：提供常用短语与“本节课共同情况”，每人保留独立观察。区分“未记录”“缺席”“本次不生成”，避免未勾选代表多种含义。
4. **批量生成**：显示待生成、处理中、失败、待确认、已完成数量；默认只生成未完成且有观察记录的人。当前批量入口只过滤 activated，空的 V2 输入仍会变成包含字段名的非空字符串进入生成。
5. **连续校对**：正文直接可编辑，支持“确认并下一位”；筛选只看失败或待确认的人。保留原始观察在旁，减少来回切换。
6. **交付收尾**：预览最终模板效果，支持纯文本和 Markdown；记录已复制时间，但不要将“已复制”误写为“已发送”。

### 键盘细节

目前 Enter 导航有价值，但根据当前人的输入版本构造下一个输入框 ID，混合 V1/V2 容易找不到目标；未排除禁用学生。输入法组合输入期间没有显式检查 isComposing，需真机验证中文选词回车是否误跳。V2 无条件阻断 Alt 组合键，范围过宽。

建议让 Tab/Shift+Tab 始终符合常规行为，再提供明确可发现的“下一位”快捷键；导航遍历实际可编辑字段，跳过禁用项。输入法、下拉建议选择、混合模式需要一起验收。

### AI 配置

API Key 目前使用普通文本框，每次输入都会保存并发提示，且要求刷新加载模型。改为密码输入、明确保存和测试连接；显示当前连接状态。不同提供商分别保存凭据，切换时不应把旧提供商的密钥自动用于新地址的模型查询。

区分常用设置与高级提示词。先让教师用清晰的长度、语气选项完成工作，再允许展开完整提示词。真实提供商支持情况和模型默认值需要单独联调核实，本轮没有验证在线服务。

## 5. 性能审查

### 实测与边界

`npm run test`：18 个文件、47 个测试通过。

`npm run build`：TypeScript 和生产构建通过，Vite 报告构建耗时约 9.96 秒。

`npm run lint`：通过。

| 主要 JS 产物 | 原始大小 | gzip |
| --- | ---: | ---: |
| vendor-react-antd | 992.23 kB | 299.45 kB |
| vendor-others | 121.17 kB | 40.49 kB |
| index | 53.24 kB | 18.24 kB |
| vendor-dayjs | 17.69 kB | 6.33 kB |

这些是构建产物大小，不是线上实际首屏流量，也不是用户响应时间。本轮没有采集生产环境 LCP、INP、网络瀑布或 React Profiler，不能据此宣称页面达到或未达到具体性能指标。

### 有明确依据的优化方向

**先缩小流式更新影响范围。** `useStudentsManager` 直接订阅整个 roster store。每个流式片段更新 studentsInfo，会让 MainUI 重渲染；传给列表的部分回调每次重建，使 memo 的收益下降。列表一次性挂载全部卡片和表单。建议每张卡片按稳定 ID 订阅必要字段，保持回调稳定，再把流式显示合并到合理时间间隔。是否虚拟化，应由 30/100 人的输入延迟测量决定，不能破坏表单保存和键盘导航。

**修正假懒加载。** SettingsDrawer 和 TemplateEditor 即使未打开也被渲染，lazy 模块仍会请求；另外还有主动预加载所有组件。首屏必需的课程卡片可直接加载，设置、模板编辑器在需要时挂载。当前 TemplateEditor 没有就近的 Suspense 边界，也应一并梳理加载体验。

**消除每个学生一次的多余客户端初始化。** `startStudentFeedbackGeneration` 默认参数创建 ProviderAIClient，即使调用者已经传入 orchestrator 也会执行；其 API 构造函数会加载配置并调用 getModelList。批量生成时会产生不必要的客户端和模型列表请求。仅在真正需要创建编排器时创建客户端，模型列表由设置流程管理。

**梳理两层队列。** 编排器限制并发 3 个，底层 API 另有限速和队列，并对所有提供商固定每分钟 10 次。界面很难解释真正的等待原因。统一任务状态来源，保留必要的并发与速率控制，按可验证的服务配置和响应处理限流，不把固定值宣称为所有提供商的限制。

**降低同步存储压力。** trace 每次保存都会读写最多 50 条完整记录，包括消息和输出；不是每个 token 都保存，但大量长文本仍可能造成主线程停顿或配额异常。改为异步存储或延后批量写入，限制字节量并支持清理。业务草稿和诊断记录应分开管理。

**最后优化构建包。** 结合产物分析确认哪些组件进入主 vendor；减少仅为设置或诊断引入的首屏依赖。不要通过提高包大小警告阈值来代替优化，也无需仅为包大小更换 UI 框架。

建议建立固定基准：10/30/100 人、V1/V2 两种输入、3 路模拟流、首次与再次加载、窄屏和普通笔记本。记录输入延迟、长任务、commit 数、请求数和完成耗时，再比较优化前后。

## 6. 可发散的产品想法

| 想法 | 用户收益 | 相对成本 | 建议 |

| “更简洁 / 更具体 / 更温和”局部改写 | 比整篇重做更可控 | 中 | 保留事实和旧稿 |

不建议近期同时扩展大量主题、模型供应商、仪表盘和外部消息渠道。它们会扩大维护面，对当前丢稿、错位和校对效率的帮助较小。也不建议用模型自动推断学生长期能力或用生成内容替代本次观察。

## 7. 建议实施顺序与验收

**第一批：可信地保存和对应数据。** 修复排序与身份绑定、任务回写保护、名单编辑保留结果、课次草稿恢复、流式解析与错误处理、导出状态过滤。补排序、切班、刷新、在途请求、重复生成、流式拆包的回归测试。

**第二批：清理操作与视觉障碍。** 修复更新弹窗和手机布局，统一动作文案、合并复制入口，加入生成总进度、正文编辑、确认并下一位、保存状态与最终预览。补键盘、输入法、备份恢复的交互测试。

**第三批：测量后优化效率。** 按学生细分订阅、合并流式刷新、移除冗余客户端创建，按基准数据决定是否增加紧凑列表或虚拟化；随后验证局部改写和历史对比的价值。

最值得补的测试不是更多 getter/setter 测试，而是完整用户场景。现有 roster 测试验证了排序后运行时输出不丢失，却没有验证 Form 中的原始表现同步排序，这正是“单测全通过、实际操作仍错位”的原因。

成功指标应同时包括可靠性与效率：错位和无法恢复的草稿事件为零；一次课从打开到全部确认的时间下降；每位学生的手工改动量和重复生成次数下降；失败能够恢复；常用设备上输入流畅。上述是后续验收目标，本轮没有真实教师使用数据来量化收益。
